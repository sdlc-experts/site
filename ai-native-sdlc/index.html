What is an AI-native SDLC?

An AI-native software development lifecycle is one where coding agents do the routine work at every step, from a request to a ready-to-merge pull request, while people make and approve the decisions that need judgment. This guide covers the six stages, where the human gates go, why a decision wiki matters, and how to start.

AI tools are not the same as an AI-native SDLC

Most teams already have AI coding tools. A few engineers get a lot out of them, most use them a little, and everyone has a different personal setup. Each new chat starts from zero, so conventions and past decisions are explained again, or ignored. Leadership pays for licenses and still can't point to faster delivery.

An AI-native SDLC changes the process, not just the editor. Every request follows the same path, agents have the context they need at each step, and the points where a person must decide are built in. The result is a team that ships through one shared flow instead of many private habits.

The six stages, from request to merged PR

Here is the flow we set up. Dark steps are human gates: nothing moves past them without a person's approval.

  1. Request. Anyone raises a bug or idea, for example from Slack or email. A ticket is created in your product tool.
  2. Spec. An agent turns the request into a spec and a plan it can execute, and attaches them to the ticket.
  3. Approve the spec. An engineer signs off before any code is written.
  4. Build. The coding agent implements and tests the change on its own branch.
  5. Pull request, preview and AI review. The agent opens a pull request with a live preview environment, and automated checks in CI catch agent mistakes first.
  6. Approve and merge. A developer does a focused review of what needs judgment, and merges.

Your product tool, such as Jira, Linear, Monday or GitHub Issues, is updated at every step, so nobody moves tickets by hand.

Where people stay in charge

The two gates are the point. Approving the spec before code is written is cheaper than reviewing a pull request built on the wrong idea. The final review is shorter because the preview environment and AI checks have already caught the obvious problems, so the developer's time goes to what needs judgment.

Security belongs in the same design: which repositories and tools agents may touch, where a person signs off, and what runs only in CI. Agents work on their own branches with the permissions you set, and nothing merges without a developer's approval.

The decision wiki: decide once

Agents forget. A decision wiki is how they stop forgetting. Each decision your team makes, such as a library choice, a naming convention or an architecture rule, is written down once and approved by a person. From then on, every agent reads it before it writes a spec or code.

It works like architecture decision records (ADRs), but for agents as well as people. Agents can propose new entries, and a person approves each one before any agent follows it. Every approval in the flow can feed it, so the next spec starts from everything your team has already decided.

How to start without rebuilding everything

  • Pick one pilot squad and one repository, not the whole organization.
  • Connect the tools you already use: your repo, tickets, tests and CI. No new tracker is needed.
  • Put the two gates in first, spec approval and merge approval, before you let agents do more.
  • Start the decision wiki with the handful of rules your team repeats most often.
  • Add a preview environment and AI review to every pull request so reviews get shorter, not longer.
  • Measure with what you already track, such as time from request to merge, and expand once the pilot squad trusts the flow.
